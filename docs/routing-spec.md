# Crossbar 写通路：地址译码与轮询仲裁

2026-11-15。继续已经批准的 4×4、AW/W/B、按地址选目标与轮询仲裁路线。本增量是内部模块，不是完成顶层连接。原有 Tracker 不改动。

## 1. 地址译码 axi_address_decode

输入 address 与 map_base/map_limit（每目标一组包含端点的地址范围），输出 map_valid、decode_error、target。默认 ADDR_WIDTH=32、TARGETS=4；目标编号 0～3 为物理 Slave，编号 TARGETS=4 为内部 DECERR 目标，与 Tracker 对齐。无时钟、无状态、无 AXI 握手；译码结果只有被上层随 AW 锁存后才属于某笔事务。

顶层首配置沿用总计划：S0=0x00000000..0x0000ffff，S1=0x00010000..0x0001ffff，S2=0x00020000..0x0002ffff，S3=0x00030000..0x0003ffff。ID 完全不进入译码模块。

map_* 由顶层常量或静态配置提供，基础阶段不支持运行中重映射。每个范围起止有效、不重叠，起点按 4KB 对齐、终点为 4KB 最后一个字节。可以存在地址空洞，也可以调整目标顺序。采用 4KB 对齐窗口，使合法且不跨 4KB 的 burst 不会在一次事务中跨越映射边界；这不代替协议 checker 对非法 burst 的检查。

合法映射下，命中则 target 为对应 Slave，decode_error=0；未命中则 target=TARGETS、decode_error=1。非法映射时 map_valid=0，全部地址都输出错误目标，不能依靠“后一个规则覆盖前一个”。上层仿真配置检查应将 map_valid=0 报为配置错误；它与正常的未映射访问不同。

此模块只输出错误目标，不产生 B、不消耗 W。后续 DECERR 处理端必须收齐 W 后响应，并参与 Tracker 顺序与容量管理。

## 2. 轮询仲裁 axi_rr_arbiter

输入 clk、reset_n、request[PORTS]、grant_ready；输出 grant_valid、grant_index、grant_onehot、request_ready[PORTS]。默认 PORTS=4，也支持 1 和非 2 的幂数。request 来自内部持久请求，grant_ready 表示下一层能真正接收这个选择。没有 AW 数据端口，payload 的存储与 mux 由通道封装负责。

每个物理 Slave 的 AW 出口计划各实例化一个仲裁器，互相独立。不用一个全局仲裁器串行化全部四个出口。首阶段 AWQOS 只传递，不改变轮询优先级。

规则：

1. 复位清锁与指针；起始搜索位置为入口 0，复位期间不输出 grant 或 ready。
2. 空闲时从指针开始循环扫描，选择第一个有请求的入口。
3. grant_valid=1 且 grant_ready=0 的采样沿保存选中入口。之后即使其他入口加入请求，也保持原选择。
4. grant_valid && grant_ready 握手后，指针移到刚完成入口的下一个，释放锁；下一周期可服务下一笔。轮完的事件是本模块向下一层的接收握手，不是 WLAST，也不是 B。
5. 没有请求或只是等待时，指针不动；空闲间隔不把指针重置到 0。
6. request_ready 仅对选中的入口置位，且仅在 grant_ready=1 时置位。grant_onehot 表示选择，即使下游不 ready 也保留。

选中后，来源必须保持请求及对应 AW payload，直到接收或公共复位。仲裁器以断言检查被锁定请求不能撤销；payload 稳定性由后续通道封装检查。不能每周期重新用变化的容量条件屏蔽已选请求；应先通过准入或在锁定时保留所需资源。

在所有入口持续请求、下游持续可接收的条件下，服务顺序为循环轮询，每 PORTS 次握手每个入口一次。下游长期背压时不承诺固定周期内完成。这里的公平性不能外推为整个 Crossbar 的无死锁证明。

## 3. 连接前必须保持的约束

Tracker 分配、上游 AW 接收、AW 信息保存与入口 W 路由记录分配须原子完成。向下游提交 AW 时，也必须有容量保存该出口的 W 来源记录；AW 握手顺序必须与来源记录顺序一致。

本仲裁器是内部选择组件，组合 request→grant 与 grant_ready→request_ready 尚未经过 AXI 端口寄存器切断，不能直接声称顶层满足 AXI 接口组合路径约束。具体 AW 缓冲放置和资源预留将在下一个连接增量一起落实。

尤其要检查跨出口 AW 重排与各入口 W 顺序之间的关系；只按每个出口独立仲裁而任意改变一个入口的 AW 发出顺序，可能造成 W 等待环。后续先完成入口/出口路由记录设计再集成，不能用单模块轮询测试冒充系统无死锁验证。

## 4. 独立自检

`dv/tests/routing/routing_tb.sv` 包含两个模块的自检。仲裁参考使用独立优先队列轮转，RTL 使用指针与锁；逐拍检查索引、onehot、ready 与接收事件。场景包括持续竞争、稀疏请求、空闲后续接、背压中新增竞争、锁定中复位、参数 1/3/4，以及主动撤销锁定请求的负向断言。

译码检查默认映射、每段首尾、重定位/空洞、64 位高地址、全 1 地址、随机段内/空洞，以及范围倒置、重叠、错误对齐。非法映射输出诊断，不误报成正常映射。

运行 `python3 scripts/run_routing.py`。参数 PORTS/ADDR_WIDTH=4/32、3/32、1/32、4/64；各 seed=7、41、2026。工具为已有本机 Verilator 5.052；警告按失败处理。结果和源摘要写到 routing-results.json，日志保存在 logs/routing。

## 5. 交付范围

新增两个可综合组织的 RTL 模块、独立 SystemVerilog TB、运行脚本和本文。没有复用上游源码，没有进行综合、形式证明或系统覆盖收敛。暂未新增 W 来源 FIFO、2 拍 W 缓冲、B 路由、错误响应端和 4×4 顶层；这些仍属后续实现范围。

## 6. 实际运行结果

12/12 次正常运行通过，1/1 次撤销锁定请求的负向测试正确触发 ARBITER_REQUEST_WITHDRAWN。四组编译均通过且未关闭警告失败策略。正常运行合计包含 12000 个随机仲裁周期和 6000 次随机地址检查，另有定向边界检查。4 入口/32 位/seed7 的一次运行实际完成 750 次仲裁接收、223 个背压周期，检查 530 个地址样例；这些是测试见证，不是系统性能指标。

逐项结果及源摘要见 [routing-results.json](routing-results.json)。原有 Tracker 的 RTL/TB 源摘要与上轮通过记录一致；本轮未修改其源码，未重复宣称重新执行 Tracker 回归。
